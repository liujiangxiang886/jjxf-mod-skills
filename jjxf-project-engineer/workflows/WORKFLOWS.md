# WORKFLOWS.md · 端到端工作流总入口

> 这份文件把「MOD 开发工程师」从**知识问答**升级为**分步引导**：
> 用户说"我想做个新内容 / 帮我打包验证 / 装了没生效"，不是甩一段答案，而是
> **按标准作业流程（SOP）一步一步带着用户走完，直到跑通**。
>
> 适用基准：**机甲旋风单机版 / 新起点启动器**这一套 Godot 启动器引擎（唯一基准）。
> 所有命令、路径、判据均来自本 Skill 的 `references/`，不臆造工具行为。

---

## 一、引导协议（每次进入工作流都遵守）

1. **一次一步**：每轮只推进当前一个步骤，给出「目标 / 操作 / 通过判据 / 下一步触发条件」，
   **等用户回报结果再进入下一步**。不一次性倾倒全部步骤。
2. **每步可判**：每一步都给一个明确的"怎么算过了"（退出码、状态、日志关键词、现象），
   让用户能自行确认；用户回报后由你对照判据判定通过 / 退回。
3. **卡住即分流**：任一步不通过，要么按该步的「卡住分支」就地修，要么路由到 `wf-5-troubleshoot.md`
   按错误码定位，**不要跳过**。
4. **纯咨询不变**：你只给步骤、命令、路径、判据并判定结果，**不擅自读写用户文件、不替用户执行命令**，
   除非用户明确说"你帮我跑"。这与 Agent MD 铁律 3 一致。
5. **每步带出处**：命令与判据标注来自哪份 `references/xx.md §章节`，用户可自查。
6. **先判基线**：进入打包/验证流前，先确认是**标准线（4.6/4.7）**还是**自定义基线**——
   两者打包验证口径不同（见 WF-3），混用会得到假阳性。

### 每一步的标准格式（输出给用户时套用）

```
【第 N 步 · 目标】这一步要解决什么
【你要做的】可直接复制的命令 / 动作 / 路径
【怎么算过了】退出码 / 状态 / 日志关键词
【过了之后】进入第 N+1 步（一句话说明下一步）
【卡住了】见 <分支或 WF-5 对应错误码>
【出处】references/xx.md §章节
```

## 二、五条工作流与分流表

| 编号 | 工作流 | 用户这样问时进入 | 详细文件 |
|---|---|---|---|
| **WF-1** | 从零开发新内容 | "我想做个新武器/剧情/数值 MOD，从哪开始" / "新手怎么开发" | `wf-1-new-content.md` |
| **WF-2** | 标准线打包与验证 | "4.6/4.7 的包怎么打包验证" / "check 怎么过" | `wf-2-build-verify.md` |
| **WF-3** | 自定义基线 MOD | "我自己改了本体/用自定义版本，怎么做 MOD" / "custom-baseline" | `wf-3-custom-baseline.md` |

**典型完整链路**：`WF-1`（做出内容）→ `WF-2` 或 `WF-3`（按基线打包验证）→ `WF-4`（安装跑通）

## 三、分流判定（用户一句话进来时，先判这个）

```
用户请求
├─ 想做全新的 MOD 内容、还没动手 ──────────────→ WF-1
├─ 已有目录/内容，要打包成可发布包
│   ├─ 目标是 4.6 / 4.7 标准线 ───────────────→ WF-2
│   └─ 目标是自定义/改版本体 ─────────────────→ WF-3（先读能力边界！）
├─ 包已打好，要装进启动器并确认生效 ──────────→ WF-4
├─ 报错 / 被剔除 / 装了没变化 / 0 命中 ────────→ WF-5
└─ 问题说不清 ─→ 先澄清三件事：
      ① 哪条线（4.6 / 4.7 / 自定义基线）
      ② 做到哪一步了（没开始 / 有内容没打包 / 有包没装 / 装了不生效）
      ③ 要改什么（数据 / 资源覆盖 / 剧情文本 / 钩子脚本）
     再按答案分流，不默认套用。
```

### 分流的硬边界（必须先讲清，否则会误导用户）

- **机甲旋风 4.7 只有 `.gdc` 字节码、不能改源码重编译、不支持自由新建角色**。
  用户若问"给机甲旋风做个全新角色/武器"，先说明只能走**数据 / 覆盖层**改，
  不能照搬通用 Godot"加节点写脚本"那套（出处：`00-project-profile.md` §谁能改什么）。
- **自定义基线（权威边界，见 `references/12-custom-baseline.md`）**：`jjm_pack` 的 `--line` 只认
  4.6/4.7（写 `custom:…` 退出码 2）；**扩展装配层未开放**（界面只有 4.6/4.7 入口），
  插桩层生成器也未接入。现在只能做三件事：启动改版、存档隔离、验收基线（`cli custom-baseline`）。
  **不存在"给自定义线打包→安装→生效"的链路**，不要给这种预期。这是 WF-3 的硬约束，进去前先讲。
- **一条线一份包**：跨线硬拒绝，不要给用户"一份通吃两线"的预期（出处：`04-author-faq.md` 避坑 1）。

## 四、工作流与知识库的关系（取证顺序）

工作流负责**流程编排**，具体事实仍从知识库取，二者不重复：

- **命令唯一正确形式 / compat 命中预检 / seal 两种指纹域 → `references/11-command-reference.md`（权威）**
- 工具退出码 / 报告字段 / 已知误报 → `references/07-tool-usage.md`
- **共存冲突真实输出 / overrides 方向性 → `references/13-coexistence.md`**
- 错误码含义与修法 → `references/03-error-codes.md`
- 最小工具链与四道关卡概念 → `references/02-mod-toolchain.md`
- **自定义基线能力边界与 B0–B5 验收 → `references/12-custom-baseline.md`（权威，覆盖 08）**
- 标准线身份重建/换剧情层 → `references/08-version-maintainer.md`
- 新手开发内容拆解 → `references/10-general-mod-dev.md`
- 最小样例包结构 → `examples/me.hello_world-1.0.0.zip`（解压）
- 真实踩坑案例 → `experiences/`

工作流的每一步都标了对应出处；若某步的判据在知识库里没有，直说"需向版本作者确认"，不编。

**取证预算（防检索回环）**：工作流每一步只按该步标注的出处读对应文件，**按错误码直查
`03-error-codes.md` 对应行，不做全文搜索**。一次回答内打开 `references/` ≤ 3 份、同一文件 ≤ 2 次、
命中即停；任一步判据未命中，立即停止翻找并按 `SKILL.md`「检索预算与未命中兜底」降级作答，
**不为找判据在文件间反复横跳或二次检索**。卡住就按引导协议第 3 条分流 WF-5，不在原地循环。

## 五、跑通的定义（WF-4 的验收终点）

一个 MOD 算"跑通"，必须同时满足四道关卡（出处：`02-mod-toolchain.md` §从 check 到生效）：

1. `check` 通过（0 error）
2. `seal` 已签封（`verification.json` 存在且与代码层指纹匹配）
3. 安装闸门通过（无 schema / 位置冲突）
4. 挂载冒烟通过：启动一次游戏，扩展页状态从 `needs_hooks`（待插桩）翻到 `ready`（已就绪），
   进游戏稳定 5 秒后仍正常

四关缺一不算跑通。`check` 全过只是第一关——这是作者最常见的误解。
